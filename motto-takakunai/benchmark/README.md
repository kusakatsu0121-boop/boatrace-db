# 「もっと高くない？」AI対抗ベンチマーク

目的: 「同じ仕事の値段違いチェッカー」が、一般AIへ直接求人を貼って探す方法より有用かを、実求人で継続測定する。

## サービスの勝負軸

求人検索の網羅性そのものではなく、以下を提示前に検証できるかを測る。

1. 同じ現場・同じ仕事の、より高い掲載中求人を見つける
2. 別仕事を同じ仕事として混ぜない
3. 掲載終了求人を最高時給候補にしない
4. 深夜割増・残業割増等を基本時給として誤認しない
5. 求人貼り付けから結果までの手間を減らす

## Ground Truth（正解セット）

発見率の分母を恣意的にしないため、各CASEで人間による正解探索を先に固定する。

### 探索ルール

- 原則30分以内で手動探索する
- 元求人の「勤務地（ビル名・施設名・最寄駅）＋特徴的な業務内容」を主要検索軸にする
- 最低限、以下を確認する
  - 主要派遣会社サイト 3〜5社
  - 求人ボックス・スタンバイ等の横断検索 1〜2系統
  - 勤務先または募集会社の自社求人ページ（確認可能な場合）
- 発見候補は詳細ページまで開く
- 「掲載中」「掲載終了」「確認不能」を分ける
- 基本時給を手動で正規化する
- 同一現場・同一仕事かを人間が確認する

### Ground Truthの3値

- `exists`: より高い掲載中の同一求人を1件以上確認
- `none_found`: 規定範囲を探索したが確認できず
- `unknown`: 探索不足・アクセス不能などで判定不能

`none_found` は「世界中に存在しない」という意味ではなく、「規定の探索範囲では実用上確認できなかった」という意味とする。

後日「もっと高くない？」や他AIが、手動探索では見つからなかった掲載中の高額同一求人を発見し、人間確認で正解と認定された場合はGround Truthを更新する。更新履歴をnotesへ残す。

## CASE選定バイアス管理

各CASEに `selection_mode` を保存する。

- `expected_comparable`: 比較できそうと判断して選定
- `random`: 比較可能性を考慮せず選定
- `rotation`: 職種ローテーションに従い選定

30件全体で3種類を混在させ、得意な求人だけに偏らせない。

職種目安:

- 倉庫・検品・軽作業 10
- 事務・データ入力 8
- コールセンター 7
- 製造・工場（期間工以外）5

難易度目安:

- easy 10
- normal 12
- hard 8

## 調整CASEと正式CASE

CASE-001〜003は運用・項目・測定方法の調整用として保存するが、原則 `scored: false` とする。
正式評価は `scored: true` のCASEだけで計算する。

調整CASEを後から都合よく正式CASEへ変更しない。正式カウント開始後は判定基準を変更した場合、その変更日と影響範囲を記録する。

## 比較対象

原則として同じ入力求人・同じ時点で以下を比較する。

- motto_takakunai
- chatgpt
- gemini
- perplexity

AI側の統一依頼文:

> 以下の求人と、同じ仕事内容・同じ勤務地（または最寄駅）・同じ時間帯で、より時給の高い求人を探してください。ただし、深夜割増を含む表記は基本時給に換算して比較し、掲載終了している求人は除外してください。

## 主要KPI

### 1. 高額同一求人の発見率

`高額同一求人を発見できたCASE数 / Ground Truth=status:exists のCASE数`

`none_found` と `unknown` は分母に入れない。

### 2. 別仕事誤判定率

`別仕事を同じ仕事として提示した候補数 / 提示候補総数`

最終目標: 10%以下。将来的には5%以下。

### 3. 掲載終了提示率

`掲載終了・応募不能求人を高額候補として提示した件数 / 提示した高額候補数`

目標: **0%**。これは総合点で相殺しない合格必須条件。

- 掲載終了を1件でも提示したCASEは `case_fail_ended=true`
- 正式CASEで1件でも発生した場合、最終合格は不可
- CASE-10時点で1件でも発生した場合、掲載状態ロジック修正を最優先にする

### 4. 基本時給正規化率

`基本時給を正しく判定した件数 / 時給比較対象件数`

最終目標: 95%以上。

### 5. 手間・時間

時間と操作を分けて保存する。

- `t1_result_seconds`: 求人入力完了 → 比較候補表示まで
- `t2_open_clicks`: 候補表示 → 実求人詳細ページを開くまでのクリック数
- `t3_total_seconds`: 入力開始 → 実求人詳細確認までの総時間

AI側も同じ概念で記録し、プロンプト入力開始から結果・求人確認までを測る。

## 同じ仕事率

0〜99%。100%は禁止。
数値だけでなく、根拠を必ず分解して保持する。

例:

- location_match
- station_match
- workplace_match
- shift_match
- task_match
- period_match
- employment_match

UIでは `✓ 勤務地一致 / ✓ 夜勤一致 / △ 期間差あり` のように説明可能な状態を維持する。

## 採点

各サービス・各CASE:

- 掲載中の、より高い同じ仕事を発見: +1
- 別仕事を同じ仕事として提示: -1
- 掲載終了・応募不能求人を高額候補として提示: -2
- 深夜割増等を基本時給として誤認: -1

合計点は補助指標。掲載終了0%・発見率・誤判定率・正規化率を優先する。

## Go / No-Go ゲート

正式CASE数で評価する。

### 10件時点

GO目安:
- 発見率 50%以上
- 誤判定率 20%以下
- 掲載終了 0件
- 正規化率 85%以上

掲載終了が1件でもあれば `STATUS_LOGIC_REVIEW` とし、新規CASE追加より掲載判定改善を優先する。

### 20件時点

GO目安:
- 発見率 60%以上
- 誤判定率 12%以下
- 掲載終了 0件
- 正規化率 90%以上

未達なら職種特化・判定ロジック変更・B2B用途を含む方向修正を検討する。

### 30件時点

PASS条件:
- 発見率 65%以上
- 誤判定率 10%以下
- 掲載終了 0件
- 正規化率 95%以上

1つでも未達なら `FAIL_OR_PIVOT` とし、本格展開前に戦略を見直す。

## 変更管理

ベンチマーク開始後に同一仕事判定やGround Truthルールを変更した場合は、READMEと対象CASEのnotesへ変更理由を残す。過去の不利なCASEを削除して成績を改善してはいけない。
